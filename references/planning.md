# 下一阶段餐单生成契约

复盘只产出目标数字（`nextGoal`）。要把数字变成可执行的 7 天餐单，由工作台「下一阶段餐单」卡用**本地确定性算法**解算 —— 不联网、不调大模型。

## 为什么是本地算法，而不是大模型

早期版本把排餐交给云端大模型（把目标 + 食材库写进提示词，让模型挑食材、配份量）。后来整体换成本地算法，原因有三：

1. **可用性**：移动端浏览器对长时间的流式请求不友好，实测在手机上点「生成下一阶段餐单」经常转圈直到失败。本地算法是同步计算，任何设备点一下即出，没有超时一说。
2. **可复现**：同一份目标 + 同一份食材库必须得到同一份餐单。模型每次输出带随机性，用户没法判断「这周和上周不一样」是目标变了，还是模型自由发挥。
3. **可追责**：每样食材的克数都能追溯到一条明确的反解公式。用户问「为什么是 165g」，能给出答案。

代价是变化度下降 —— 算法是确定性的，靠「换一种搭配」（递增 `seed` 改变轮换起点）提供有限的变化。

## 算法结构

`generatePlanLocally(review, seed)` 全程同步、无网络请求。四步走：

1. **分配**：每日目标按三餐配比（`MEAL_SPLIT`）拆成每餐的碳水 / 蛋白目标。
2. **选材**：每餐两个槽位 —— **主食**跟随 `pack.staples`、**蛋白源**跟随 `pack.proteins`，各自按天轮换。
   脂肪不进候选池：早餐南瓜子与晚餐混合坚果是**每天固定的量**（`pack.fatFixes`），直接压进那一餐。
3. **两遍解算**：
   - 第一遍只盯碳水与蛋白，量出「食材自带了多少脂肪」；
   - 缺口 = 每日脂肪目标 − 自带脂肪，按午 4 : 晚 3 摊到两个正餐，用**烹调油**补足（早餐不炒菜，不参与）；
   - 第二遍把油放进来，盯住碳 / 蛋 / 脂三项反解出所有克数。
4. **取整**：把克数落到人能执行的步进上，并剔除碎片条目。

最后蔬菜与蓝莓在解算之后追加（它们不计碳蛋脂，不会干扰配额）。

## 餐次配比（`MEAL_SPLIT`）

| 餐次 | 碳水 | 蛋白 | 脂肪 |
| --- | --- | --- | --- |
| 早餐 | 30% | 30% | （不设目标） |
| 午餐 | 40% | 40% | 油分配权重 40 |
| 晚餐 | 30% | 30% | 油分配权重 30 |

早 3 : 午 4 : 晚 3 的用意是**白天多供能、晚间收一收**，与主食口径（早燕麦 / 午米面 / 晚薯类）同向。

脂肪这一列**不再当作三餐目标**：早餐没有可调脂肪源，硬凑只会扭曲鸡蛋份数；午餐与晚餐的脂肪目标由「食材自带 + 分配到的油缺口」现算（见上文两遍解算）。表里的 40 / 30 只作为**油缺口的分配权重**。

餐次时间固定 `MEAL_TIMES`：早餐 08:00、午餐 12:30、晚餐 18:30。

## 候选池（`slotCandidates(kind, meal, target)`）

只处理两个槽位，两者都是**硬口径**（只在该餐候选为空 = 不限定时才回落到全库）：

| 槽位 | 口径来源 | 回落到 |
| --- | --- | --- |
| `staple` | `pack.staples`（餐次主食安排） | 全库「主食」类 |
| `protein` | `pack.proteins`（餐次蛋白安排） | 全库「蛋白质」类 |

回落时仍按餐次习惯分组（早餐先蛋奶、正餐先肉类蛋白），免得「不限定」变成「早餐瘦牛肉 100g」。

**密度闸门**：剔除「要吃到离谱份量才够」的食材 —— 按个计的最多 6 个，按克计的最多 350g。牛奶蛋白密度只有 3.3g/100ml，得喝 800ml 才顶一餐蛋白，自带碳水还会把额度顶穿，所以它和酸奶都会被请出候选池。池子被清空时回退到不过滤，保证总有食材可用。

**显式豁免**：用户在「餐次蛋白安排」里明确勾选的，一律放行，不受密度闸门过滤 —— 用户的选择优先于算法的效率判断。

> 历史变更：早期还有一份跨餐次的「下一阶段优先食材」（`foodLibrary.selected`）也享受同样豁免。三块按餐次的硬口径上线后它已被移除（两套规则会互相打架），豁免范围收敛为「该餐显式配置的蛋白」。

**排序**：低脂优先（脂肪 / 蛋白比升序），7 天轮换时先排清淡的，口味与脂肪都更稳。

> 历史变更：早期版本有**脂肪源候选池**（按密度降序在橄榄油 / 混合坚果 / 南瓜子 / 牛油果里轮换），并为此配了「脂肪预算闸门」「早餐限定蛋奶」「早餐蛋奶豁免闸门」三条补丁。现在坚果与南瓜子改为每天固定的摄入量、其余脂肪一律用油补足，这些补丁**全部删除** —— 早餐不再出现正餐肉，是因为 `pack.proteins.breakfast` 本来就只有全蛋，不需要在算法里再打补丁。

## 反解与取整（`solveMealAmounts`）

**不能用一次性顺序反解**。食材是互相渗透的 —— 奶带碳水、鸭腿带脂肪 —— 一次性解会让后选的槽位把前面已经算好的额度顶穿（实测碳水偏差可达 37%）。

做法是带阻尼的迭代，签名 `solveMealAmounts(target, picks, kinds)`：

1. 初值：各槽按自己的主责宏量反解（主食 → 碳水、蛋白源 → 蛋白、油 → 脂肪）。
   带 `fixed` 的项（南瓜子 / 混合坚果）直接用固定克数，**不参与迭代**。
2. 每轮算残差，按 `残差 / 该食材该宏量密度 × 0.8` 回灌到对应槽位；0.8 是阻尼，防高密度食材（油脂）过冲。
3. `kinds` 指定本次盯住哪几项宏量：早餐只盯碳水与蛋白（没有可调脂肪源，脂肪是自然产物），午晚盯三项。
   三项相对误差都小于 1% 即收敛；上限 60 轮。无解时（例如脂肪目标已被肉占满）油槽自然被压到 0。

取整与清洗：

| 槽位 | 步进 | 保留下限（低于此值视为碎片剔除） |
| --- | --- | --- |
| 主食 / 蛋白源 | 5g | 10g |
| 烹调油 | 2g | 2g |
| 按「个」计的（鸡蛋） | 1 个 | 1 个 |

**油的下限只能取一个步进**：油本来就按小份量用（一勺十几克），若沿用 10g 下限，「6g 油」会被当碎片误杀，当天脂肪会直接塌掉（实测−16%）。固定项按原样输出，不取整、不清洗 —— 它就是要每天吃那么多。

剔除碎片后不重算，由此产生的偏差通常远小于 ±12% 的绿灯阈值。

## 固定追加项

- 午餐、晚餐各加 200g `蔬菜`（`VEG_AMOUNT`）
- 早餐加 50g `蓝莓`（`BERRY_AMOUNT`）

两者在食材库里都是零宏量占位，所以放在解算之后追加，不会影响配额。

## 输出结构

与旧版完全一致，落库格式不变：

```json
{"days":[
  {"day":1,"date":"YYYY-MM-DD","weekday":"三","reviewDay":false,
   "meals":[
     {"id":"m1","name":"早餐","time":"08:00",
      "ingredients":[{"name":"燕麦片","amount":60,"unit":"g"}]}
   ]}
]}
```

日期骨架由 `planDateSkeleton()` 本地生成，7 天中恰有 1 天 `reviewDay: true`（落在周五）。

## 校验规则（`validateGeneratedPlan`）

本地产出同样要过这道关，任一条不通过即抛错、**不落库**：

1. `days` 为非空数组；
2. 每天必须有 `date` 与非空 `meals`；
3. 餐次 `name` ∈ `早餐` / `午餐` / `晚餐` / `加餐`；
4. 每餐 `ingredients` 非空，每项有 `name`，`amount` 为正数（缺 `unit` 时补 `g`）；
5. `days.length === 7` 时，`reviewDay` 必须恰为 1 天。

## 失败处理

本地算法没有网络依赖，失败面很窄。仅当食材库为空、目标缺失等输入异常时会抛出，界面展示具体原因 + 「重试」按钮。任何情况都**不静默失败**，也不写入半成品。

## 落库与归档（`applyGeneratedPlan`）

用户点「应用到本周计划」后：

1. 现有 `weeklyPlan.days` 非空时，整体归档进 `history.weeks[]`（并记下当时的 `goal`）；
2. 写入新 `weeklyPlan`：`weekIndex` 递增，`startDate` 取新餐单首日，标记 `generatedBy: "local-solver"` 与 `generatedAt`；
3. `confirmed: true`（用户已显式点击应用）；
4. 保存并提示。

## 每日宏量核算（`planDayMacros`）

生成结果只存食材与份量，不存宏量快照（与 `favoriteMeals` 同思路）。预览时按 `findFood(name)` 查当前食材库实时折算，再把每天合计与目标对比，落在 ±12% 内标绿。这样食材库调整后，预览数字自动跟随。

实测偏差（默认口径）：

| 输入 | 碳水 | 蛋白 | 脂肪 |
| --- | --- | --- | --- |
| 59kg 女 / 一周四练 | ≤1.0% | ≤1.3% | ≤1.4% |
| 70kg 男 / 中频 | ≤0.6% | ≤0.5% | ≤1.9% |
| 同上，换一种搭配（seed=1） | ≤1.0% | ≤1.6% | ≤1.5% |
| 边界：用户自选午餐蛋白 / 改固定脂量 / 全部不限定 | ≤1.9% | ≤2.9% | ≤2.5% |

全部落在绿灯区内。

## 餐次主食安排（`pack.staples`）

谭师口径：**燕麦只在早餐、午餐默认大米、晚餐默认薯类轮换**（源于 [methods/lifestyle.md](methods/lifestyle.md) 三餐结构表）。内核是碳水按「GI + 饱腹感 + 活动量」匹配餐次 —— 白天活动多、需快速供能 → 米面；晚间活动少、要压住食欲 → 高纤低 GI 薯类。**这是默认值，不是写死的规则**。

数据结构（顶层可选字段，字段缺失即回落默认）：

```json
"staples": {
  "breakfast": ["oats"],
  "lunch": ["rice"],
  "dinner": ["sweet-potato", "purple-potato", "potato", "beibei-pumpkin"]
}
```

- 取值 `fooddb.json` 的食材 `id`；某餐为**空数组 = 该餐不限定主食**。
- `mealStaples()` 读取时会过滤掉已隐藏 / 已删除的 id，历史配置不会指向不存在的食材。
- 界面入口**只有一处**：复盘卡「餐次主食安排」区，调用 `openStaplePicker()`，**保存即持久化**（不依赖复盘「确认并生效」—— 选主食和定目标是两件独立的事）。
- 主食池由 `stapleNames()` 统一取名，避免两处口径走偏。

### 薯类份量会自动放大

薯类碳水密度远低于米面（红薯 22g/100g，大米 78g/100g）。因为算法是按碳水目标反解克数，所以排到薯类的那一餐份量会**自动按密度放大** —— 600g 红薯对应 600g 米饭的碳水，这种事不需要额外提示词，是反解的必然结果。

## 餐次蛋白安排（`pack.proteins`）

和主食同源的问题：**蛋白来源也必须按餐次分开**。全部食材混在一起轮换，7 天里必然会轮出「午餐 7 个鸡蛋」「早餐鸡胸肉 55g」这类不成立的组合。

谭师口径（同样源于三餐结构表）：

| 餐次 | 蛋白来源 | 默认 id |
| --- | --- | --- |
| 早餐 | 全蛋 | `egg` |
| 午餐 | 白肉或虾仁 | `chicken-breast` / `chicken-thigh` / `basa-fish` / `mackerel` / `shrimp` |
| 晚餐 | 瘦牛肉 | `beef-lean` |

```json
"proteins": {
  "breakfast": ["egg"],
  "lunch": ["chicken-breast", "chicken-thigh", "basa-fish", "mackerel", "shrimp"],
  "dinner": ["beef-lean"]
}
```

- 结构与 `staples` 完全一致（早 / 午 / 晚三个键，元素为食材 `id`，空数组 = 该餐不限定）。
- 候选来自全库归一后的「蛋白质」类（肉类蛋白 + 蛋奶 + 蛋白粉），由 `openProteinPicker()` 勾选。
- 界面入口同样**只有一处**：复盘卡「餐次蛋白安排」区，**保存即持久化**。
- 多候选择按天轮换，排序低脂优先。

> 谭师方法论的「白肉可选」还列了鸭腿（去皮更优），但鸭腿脂肪 14g/100g，会让整餐脂肪直接顶穿，默认口径未纳入。需要时可在候选里自己勾上。

## 每日固定脂肪（`pack.fatFixes`）与烹调油

**坚果与南瓜子不是可调脂肪源，而是每天固定的摄入量**：早餐南瓜子、晚餐混合坚果，每天重复同样的克数、不参与轮换。除此之外的脂肪，一律由**烹调油**在午餐 / 晚餐补足。

```json
"fatFixes": {
  "breakfast": { "id": "pumpkin-seed", "amount": 10 },
  "dinner": { "id": "mixed-nuts", "amount": 15 }
}
```

- 只作用于 `breakfast` / `dinner` 两个键（与方法论三餐结构表一致）；`amount` 设为 0 或 `id` 为空 = 取消该项。
- **注**：原方法论三餐结构表只写了「南瓜子 / 混合坚果」两样食物，**未给克数**。默认 10g / 15g 由用户设定，可在复盘卡「每日固定脂肪」区调整。
- 烹调油固定取 `olive-oil`（食材库缺失时回落到任意「纯油脂」= 碳 0 蛋白 0 的脂肪类食材）。它与固定项一起构成当天全部脂肪来源的兜底。
- 界面入口同样**只有一处**：复盘卡「每日固定脂肪」区，调用 `openFatFixPicker()`。

以 59kg 女 / 一周四练（日脂肪目标 64.9g）为例：早餐鸡蛋 + 燕麦 + 南瓜子约占 20g，午餐白肉 + 米自带约 3g，晚餐牛肉 + 薯类 + 混合坚果约 13g，剩下约 29g 由午餐 16g + 晚餐 12g 的烹调油补齐。

## 预览合规提示（`planIssues`，非阻断）

预览时对每天逐餐做三类检查，命中即在该天卡片下输出一条黄边条提示，**只提醒、不拦截**：

1. **主食**：该餐完全没有主食类食材，或主食不在 `pack.staples` 的候选内；
2. **蛋白**：该餐完全没有蛋白类食材，或蛋白不在 `pack.proteins` 的候选内；
3. **固定脂肪**：该餐应有的南瓜子 / 混合坚果没有出现，或份量少于设定值。

某餐候选为空（= 不限定）时跳过对应检查。

## 想调整餐单该改哪里

| 想改什么 | 改哪个常量 / 字段 |
| --- | --- |
| 三餐碳蛋配比 | `MEAL_SPLIT`（app.mjs） |
| 克的步进 / 碎片下限 | `AMOUNT_STEP` / `MIN_AMOUNT`（app.mjs） |
| 油缺口的午晚分配权重 | `MEAL_SPLIT[].fat`（app.mjs） |
| 蔬菜 / 蓝莓份量 | `VEG_AMOUNT` / `BERRY_AMOUNT`（app.mjs） |
| 食材密度闸门阈值 | `slotCandidates()` 里的 `allows` |
| 某餐吃什么主食 | `pack.staples`（界面上是复盘卡的「餐次主食安排」） |
| 某餐用什么蛋白 | `pack.proteins`（界面上是复盘卡的「餐次蛋白安排」） |
| 每天固定吃多少坚果 / 南瓜子 | `pack.fatFixes`（界面上是复盘卡的「每日固定脂肪」） |
| 用哪一种油 | `cookingOil()` 里的 `olive-oil` 优先项 |
| 餐单变化度 | 「换一种搭配」按钮递增的 `seed` |
| 按「个」计食材的取整步进 | `PIECE_STEP`（app.mjs，固定为 1 —— 不接受半个鸡蛋） |

调完 `app.mjs` 记得跑 `scripts/check_cache_versions.mjs`，并把改动同步到 `assets/frontend-template/`。
